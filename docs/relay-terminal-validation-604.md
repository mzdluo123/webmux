# Relay 终端优先补测：issue #604

本页回答“CLI agent、Vim 一类交互中，哪个方案的按键响应更好”，与[首轮验证报告](relay-validation-604.md)一起阅读。
测试使用同一台 Windows 电脑和 `172.233.136.221`，继续由 Windows OpenSSH 管理服务器；测量直连，排除环境代理。

## 判断与使用建议

**WSS + smux v2、双角色连接、服务器 BBR 仍作为 MVP 默认基线。** 这是综合按键、输出完成和工程成本的选择，不是“WSS 在任何负载都最快”。
原生 QUIC Reno 在弱网轻输出下略占优，但高刷新率退化，受损档重输出在夜间和上午均未按期完成；Hysteria BBR 可以完整推进重输出，却未稳定降低同 PTY 按键尾延迟，保留为优先复验候选。
当前路径没有证明接近本地的 Vim 手感；要同时看按键、输出推进、Ctrl-C 和恢复，不能用峰值 Mbps 代替。

最先要改善的是实际线路或缩短路径。当前 A、B 都经过同一公网路径，真实 PTY 回显约需两段 RTT；仅换 B 协议不能达到本地 Vim 的手感。
现有 P2P 直连可能减少绕行，但本轮未测 P2P，也未修改其候选限制。性能结论以本页的实测值为依据。

## 怎样测按键

- 实际 WebMux 后端、真实 Linux PTY；输入随机标记，直到收到该标记的 PTY 输出才确认，既不用本地预测回显，也不用 Write 返回时间。
- 每 250 ms 独立安排一次输入。发送和接收分开；前一个输入没有回显时仍继续安排，避免长停顿被串行请求掩盖。
- 主负载在**同一个 PTY/同一条 WebSocket**按目标速率 8 KiB/s 持续输出，约 50 次/s 更新；每轮 30 s，两轮交替顺序。
- 输出目标是生成器速率，实际吞吐会受背压影响；原始结果记录接收字节量。
- 这模拟 CLI agent/TUI 的网络负载，不是启动真实 Vim/CLI agent；没有浏览器 DOM、xterm 渲染、光标动作或人类主观评分。
- 所有已安排输入均进入分母，含发送排队/错误。逻辑期限 8 s；未确认计为失败，分位数同时给出 8 s 封顶的全输入分布。
- p95/p99 由合并原始样本排序取索引 `floor((n-1)*q)`；两轮不能证明普遍优劣，相关输入不是独立网络试验。
- 字节标记、Token、Cookie、正文和客户端公网 IP 不进入证据；每次结果保留时间、延迟、布尔完整性及聚合计数。

## 路径、拥塞控制与新控制条件

```text
按键客户端（Windows） → A：公网 HTTPS/WSS → 远程 Relay
                          → B：宿主预建反向通道 → 同机 WSL WebMux / PTY
```

A 使用 Windows 原生 CTCP；B 的 WSS TCP socket 两端指定/核实 BBR，WSL 全局默认 CUBIC 不变。
QUIC v0.65.0 使用 Reno；KCP nc=1 关闭自身拥塞窗口，均不称为 BBR。Hysteria v2.13.0 使用用户态 BBR standard，未配置固定带宽/Brutal。
服务端物理 eth0 保留 mq/fq_codel；本批统一关闭 eth0 及实验 veth 的 GRO/GSO/TSO，保存变更前与运行期记录。
因此本批不与首轮默认 offload 条件合并排名，也不能仅将前后差异归因于算法。
UDP socket 缓冲、MTU、依赖及构建指纹在证据中；没有为某个候选单独提高系统 UDP 缓冲。

`clean` 只表示不注入人工损伤。夜间自然 UDP 200 次探测往返丢包为 10%、RTT 中位数 316 ms，夜间线路与首轮不相同。
上午另探 200 次：自然往返丢包 0%、RTT 中位数 260 ms；loss3 为 6.5%、273 ms。只有离散探测，不能当成每轮的持续丢包率。
`loss3` 在 B 的两个方向各叠加随机 3% 丢包和 5 Mbps；A 不受人工损伤，仍经过真实 WAN。夜间该档 200 次 UDP 探测往返丢包 12.5%，不是每轮连续监测值。
`burst` 在 B 双向使用 gemodel 1%/25%/80%/0.1%，各 5 Mbps。上述配置不是端到端丢包率承诺。
损伤仅匹配实验端口；SSH 管理不经过 netem，后台下载、构建与压测不并行。

night 为新加坡时间 11 月 14 日晚至 15 日 00:15；随后执行环境长时间中断，morning 从 15 日 10:36 恢复。
中断落在首个 burst/WSS 的建链准备阶段，原始 host_ready_s=37243.16 保留，不能作为正常冷建链性能；其按键阶段在恢复后才开始，但该次连接年龄不可比，整轮排除性能排名，保留恢复检查并重测。
两批不合并分位数。上午重新探测路径，补 WSS/QUIC 的 32 KiB/s 对照及 QUIC 重输出；上午和夜间对照分列，不能将时段变化算成协议收益。

## 主要结果：同一 PTY 输出 8 KiB/s

WSS p2 为两条 TCP、原生 QUIC p2 为两条 QUIC、KCP p2 为两个 KCP 会话；Hysteria 的 p2 特例见下一节。

## 补充：Hysteria BBR 的反向适配

普通 Hysteria TCP forwarding 不自动支持宿主注册。本次仅为实验增加受限反向适配：
宿主经 Hysteria 的本地 TCP forwarding 拨固定 Relay 回环目标，再运行内层 TLS 1.3/mTLS + smux v2 和原型反向注册。
服务端固定 ACL 只允许此目标；外层正常 CA/SNI 与随机密码校验，不使用 skipVerify 或 0-RTT。
两个 smux 角色连接是**同一个 Hysteria QUIC 连接中的两条 stream**；每条 smux 内的终端仍共享有序 stream。
这与原生 QUIC 每代理连接独立 stream 不同，也与 WSS 两条独立 TCP 不同，包含额外 TLS/进程开销，不能据此隔离比较 BBR 与 Reno 算法。

第二组在加入适配后，Hysteria/WSS/原生 QUIC pool=1 相邻交替各两轮，沿用相同 8 KiB/s 按键负载；与第一组分列，不混成同时发生的试验。

夜间配对组受损档的 p95：原生 QUIC 单连接 1.30 s、Hysteria BBR 1.47 s、WSS 1.55 s。自然档三者约 1.13–1.16 s，差距很小。
BBR 并没有让所有按键都即时响应；Hysteria 的价值还要看更高输出时能否持续推进。两轮数据不能给出多网络通用冠军，也不能直接隔离算法收益。

## 高输出、批量并发和 Ctrl-C

重负载分阶段：空闲 15 s；另一个 PTY 以 256 KiB/s 输出 20 s；随后真实 `/forward/*` 下载 20 s。
下载源声明 1 GiB，但本次故意到时取消，只校验已读前缀的每个字节；不是又完成了一次 1 GiB 文件下载。
高输出 PTY 收到启动标记后才开始生产，避免测量开始前已积累回放。20 s 后发送真正的 Ctrl-C，最多等 12 s 的进程退出帧。
退出前发送产出字节总数，只有接收量等于总数加计数帧、且观察到退出才算输出完整；未收齐计数帧不推断产出为零。

夜间原生 QUIC p1/p2 各两轮、上午 p1 一轮均未在预算内收齐重输出及退出计数，虽然交互终端的按键分位数仍较低。WSS 和 Hysteria 的已完成重输出轮次均可收齐；必须将这两类指标一起读。
Hysteria 两轮分属夜间/上午，不合并成一次固定网络重复；上午 FEC 两轮没有同阶段的无 FEC 配对，不能据此隔离计算 FEC 收益。其下载期间交互仍有明显长尾。
双角色连接隔离批量下载，不会消除 control 内多个高输出终端的竞争。生产实现仍须验证有界背压、每流预算和慢端处理。

这是有期限的完成检查。超时不证明协议丢失可靠字节，也不能把没收到的输出忽略后宣称整体终端体验优秀。
Ctrl-C 计时包含输入传递、远端处理、已排队输出排空和退出通知到达，不是单纯内核信号投递时间。

# 官网定位与信息架构

官网的第一要务不是“展示功能”，而是让目标用户在十秒内明白这是什么、与自己有什么关系，然后完成一次成功安装。本页定义受众、价值主张、证据、叙事顺序与度量方式，后面各页都以此为准。

## 官网要解决的问题

目前唯一入口是 GitHub README。它有三个硬伤：页面标题与描述由 GitHub 控制，中文长尾搜索很难命中；无法按访客操作系统给出安装命令、无法统计转化；无法承载品牌与信任内容（安全模型、对比、更新日志）。

官网目标按优先级排列：

1. **理解**：首屏让访客明白“在浏览器里持续运行的终端，用来远程遥控 Claude Code、Codex 等 CLI agent”。
2. **转化**：把访客变成一次成功安装。核心转化事件是“复制安装命令”或“点击下载”。
3. **留存**：已安装用户能在官网文档中心快速找到答案，并在新版本发布后回访。文档镜像同时是搜索流量的主要来源（见 [SEO 规范](seo.md#内容规则)）。

明确的非目标：不做账号与登录、不做在线试用 shell（会把 shell 暴露给公网，违背 [安全策略](../../SECURITY.md)）、不做定价页、不做社区论坛。

## 目标用户

每类用户对应一组搜索意图与一个承接页面；首页必须同时照顾前两类，其余由专门页面承接。

- **远程跑 agent 的开发者**：在服务器、家中工作站或云主机上运行 Claude Code、Codex、OpenCode。痛点是离开电脑后 agent 停下来提问没人回答，手机上用 SSH + tmux 操作 TUI 很痛苦。搜索词如“Claude Code 手机”“远程 Codex”“浏览器终端 持久会话”。承接页：首页、各 agent 落地页。
- **已有 ttyd / tmux / mosh 方案的运维型用户**：关心单二进制、资源占用、systemd / launchd、安全边界与 Origin 检查。搜索词如“ttyd 替代”“web terminal persistent session”。承接页：对比页、安全页、下载页。
- **Windows 用户**：在 WSL 2 中运行，关心托盘程序、安装程序与控制台客户端。承接页：Windows 落地页。
- **中国大陆用户**：关心镜像下载与网络可达性。承接页：下载页的镜像开关与说明。
- **贡献者与 agent 开发者**：关心架构、协议、OpenSpec 与 `OSC 7501` 等状态协议。承接页：官网文档中心的架构与协议页，以及 GitHub。

## 价值主张与消息层级

一句话定位沿用 README：**在浏览器里持续运行的终端，为远程遥控 Claude Code、Codex 等 CLI agent 而生。**

信息分三层，首页从上到下按层展开，任何页面不得跳过上层直接堆功能：

1. **定位**（一句话 + 一张主图）：主标题用结果导向的场景句，候选为“让 agent 在服务器上一直跑，你在任何设备上随时接管。”副标题说明形态：单二进制、会话放在服务端、浏览器 / 手机 / 本机终端只是附着。
2. **六个卖点**（沿用 README“为什么会爱上它”）：断线不断会话、原样运行你的 agent、TUI 与聊天一键切换、等你时会告诉你、写代码的工作台、轻到可以忘了它。
3. **功能清单**（沿用 [项目介绍](../overview.md)）：会话与终端、Agent 协作、代码与仓库、多设备与平台、部署与访问。

主标题写作规则：动词开头或结果开头；不超过 20 个汉字或 10 个英文单词；不用“最”“唯一”“革命性”；每个卖点标题 4–8 个汉字，副句一句话说清收益而不是机制。

## 证据点

营销学上的“证据”是能被核实的事实。官网每个数字都要能回溯到仓库文档或 Release 资产，并由构建脚本自动取得；以下为可用的证据清单（来源见括号）：

- 单二进制，Linux amd64 约 20 MB（Release 资产大小，构建期读取）。
- 空闲常驻内存约 13 MB，一个 shell 会话约 18 MB（[项目介绍](../overview.md#高性能低占用)）。
- 每会话 2 MiB 字节环形缓冲，重连只补发缺失部分（[项目介绍](../overview.md#高性能低占用)）。
- 预置十一款 CLI agent 启动配置（[CLI agent 接入](../cli-agents.md)）。
- 七款 agent 支持 TUI 与聊天视图互切（[混合会话](../hybrid-sessions.md)）。
- 终端分屏最多 8 个窗格；Kitty 图形协议；Web Push 锁屏提醒（[项目介绍](../overview.md#特性)）。
- Linux、macOS、Windows（WSL 2）；无需 root、tmux、数据库或 Node 运行时；MIT 许可。
- 安装脚本校验 SHA-256，默认装到用户目录，不需要 sudo（[安装与升级](../deployment/install-and-upgrade.md)）。

禁止事项：不写未实现的能力（OpenSpec 中只有规划的内容不算）；不与第三方做不可核实的性能比较；边界必须写明——服务重启会结束终端会话、不是进程沙箱、不要把服务直接暴露到公网。诚实的边界说明本身就是对运维型用户的信任信号。

## 首页叙事结构

按 AIDA 组织首页，每个区块只承担一个任务：

| 阶段 | 区块                         | 任务                                       |
| ---- | ---------------------------- | ------------------------------------------ |
| 注意 | Hero：标题、副标题、主图     | 十秒内说清定位，给出主 CTA                 |
| 兴趣 | 三步看懂                     | 用“电脑开工 → 手机接管 → 回来审阅”讲故事   |
| 欲望 | 六卖点 + 界面一览 + 混合会话 | 用真实截图证明每个卖点                     |
| 行动 | 安装区块                     | 按操作系统给出可复制命令，附镜像与校验入口 |
| 信任 | 安全与边界、对比、FAQ        | 回答“安全吗”“和 tmux / ttyd 有何不同”      |
| 延续 | 页脚：文档、更新日志、GitHub | 把已安装用户导向文档与回访入口             |

主 CTA 全站只有一个语义：“安装”。次 CTA 为“查看 GitHub”或“看演示”。不要在首屏同时放三个以上按钮。

## 差异化与对比规则

对比对象限定为用户真实会拿来比较的方案：SSH + tmux、ttyd / gotty、mosh、VS Code Remote Tunnels、code-server，以及各类“手机上用 agent”的客户端。对比表只列可核实的事实维度，不做主观评价：

- 浏览器断开后会话是否继续、重连是否只补发缺失输出。
- 手机上的 TUI 适配：软键栏、触摸滚动、键盘视口。
- 是否识别 agent 的提问 / 授权请求并推送到锁屏。
- 是否提供聊天视图与 TUI 的互切。
- 是否单二进制、是否需要 root、是否需要额外守护进程或数据库。
- 是否在终端旁提供代码与 Diff 浏览、worktree 管理。

对方的情况以其官方文档为准，表下注明核对日期；拿不准的格子写“未核实”，不要猜。对比页的目的不是贬低对方，而是帮用户判断适用场景，必要时写明“如果你只需要 X，用 Y 更简单”。

## 转化漏斗与度量

- **事件**：主 CTA 点击、安装命令复制（区分操作系统与镜像开关）、下载资产点击、GitHub 与 Release 跳转、文档页进入、FAQ 展开、语言切换。
- **指标**：首页到复制安装命令的转化率、下载页停留与跳出、文档页深度、7 日回访率、各语言占比。
- **北极星指标**：每周“安装命令复制 + 下载点击”总数。它最接近真实安装，又不需要在产品里埋遥测。
- **工具**：无 Cookie 的隐私友好统计（Cloudflare Web Analytics、Plausible 或自托管 Umami 任选其一），不加 Google Analytics，不弹 Cookie 横幅。
- **节奏**：每月看一次搜索平台的查询词与站内事件，调整文案与页面；每季度复核一次证据点是否仍然成立。

## 内容来源与单一事实来源

- 文案：README 与 [项目介绍](../overview.md) 是产品描述的事实来源；官网改写措辞但不改变事实。
- 数字：版本号、资产大小、校验值、发布日期来自 GitHub Releases API，构建期读取。
- 截图：`docs/images/` 下由 `pnpm --dir web screenshots` 生成的图片；UI 变化时先更新仓库截图，再同步到官网。
- FAQ：以 [常见问题](../faq.md) 为准，官网版本可以增加“安装”与“购买 / 许可”类问题。
- 更新节奏：每次 Release 自动重建站点；产品行为变化时，先改仓库文档，再改官网。

# WebMux 用户文档写作与质量指南

适用于 `README.md`、`docs/`（面向用户的说明、部署、使用、FAQ 与官网同步文档）、`CONTRIBUTING.md` 与 `SECURITY.md`。这些文档会直接镜像到官方网站 `/docs/` 供真实用户阅读（见 [文档镜像](../../../docs/website/stack.md#文档镜像)）。

权威门禁以 [文档治理](../../../docs/doc-governance.md)、[User Stories 维护](../../../docs/agent-rules/user-stories-maintenance.md) 与 [官网定位与文案规则](../../../docs/website/pages.md#文案规则) 为准。本 skill 给出面向网站读者的组织方式、由浅入深的写作结构与自检清单。

## 核心原则：像网站读者那样组织文档

网站读者带着具体问题或任务进入某一个 URL，通常先扫读首屏和二级标题，确认“这页是不是我要找的、我第一步该点哪里”，需要时再往下看边界与协议细节。

1. **由浅入深（金字塔结构）**
   - **第一层（前 3–5 行）：这一页帮我做什么 + 最短路径。** 开头用一两句话说明本页解决什么场景、最快怎么上手（例如“在左侧切到聊天模式，选好仓库和 Agent 输入任务即可开始”）。不要一上来就抛底层协议、状态机或异常分支。
   - **第二层（主体章节）：按用户的真实操作顺序展开。** 先写日常高频操作（怎么打开、怎么选、怎么用），再写可选配置（怎么改默认行为、怎么加模板）。
   - **第三层（章节末尾或独立深水区）：边界、限制、排障与底层机制。** 把极少遇到的故障恢复、协议转义序列（如 `OSC 7501` 字节格式）、存储锁冲突或平台差异放在章节后半部分或专门的子页面，避免阻塞新手上手。
2. **用户视角，行动导向**
   - 句子以**用户能看到的界面或能做的动作**开头（“在侧栏点击「新聊天」，选好仓库和 Agent 后发送”），而不是以内部实现或接口开头（“前端向 `POST /api/quick-starts` 发送请求，服务端创建 worktree”）。
   - 界面文案使用产品中的真实名称，并以「直角引号」或“双引号”标出，写明入口位置（例如“侧栏底部的「添加仓库」按钮”“首页工具栏的「仓库设置」”）。
   - 不使用“简单”“轻松”“只需”等主观词；直接写出具体步骤。
3. **可扫读（Scannable）**
   - **先结论后细节**：每段或每条列表首句给出结论或动作，条件、原因与例外紧跟其后，不把关键前提藏在长句末尾。
   - **一句一事**：单行不超过 300 显示列（汉字与全角标点算 2 列）。遇到复合长句时，按步骤（有序列表）、并列项（无序列表）或角色拆分，绝不机械硬折行。
   - **善用对比表与提示块**：多种模式或方案的选择先给一张对比表（“我该选哪个”）；高风险边界（如暴露公网 Shell、强制删除 worktree）使用 `> [!WARNING]` 或 `> [!CAUTION]` 醒目提示。
4. **信息守恒（重构而非压缩）**
   - 让文档通俗易懂，靠的是**调整阅读顺序和拆分主题**，而不是删减事实。
   - 所有的前置条件、数值上限、配置项名、路径、安全边界、失败行为与平台限制都必须完整保留——只是从“堵在第一段”移到“操作步骤下方的说明或进阶小节”。

## 页面类型的标准结构

### 1. 入口与总览页（`README.md`、`docs/README.md`、`docs/usage.md`、`docs/deployment.md`）

- 首段一句话说清定位，紧接一張或一组“你想做什么 → 去哪一页”的导航表 / 分组列表。
- 刚接触项目的读者必须在首屏看到“最快上手路径”（如安装后的第一步、打开网页后的核心工作流）。
- 当主页面超过治理上限的 90%（约 360 行或 44 KiB）时，按主题拆分为 `docs/<主题>/<子主题>.md`，主页面保留清晰的导览与高频摘要，避免长文堆砌。

### 2. 功能与操作指南（`docs/usage/*.md`、`docs/hybrid-sessions.md`、`docs/cli-agents.md`）

按以下顺序组织每个功能：

1. **一句话价值**：这个功能解决什么痛点（例如“代码工作区让你在终端旁直接看文件、审阅 Git Diff，并把行号引用一键发给 Agent”）。
2. **快速上手 / 常用操作**：用 2–4 个步骤或清晰的要点写明怎么打开、怎么完成最核心的事。
3. **进阶选项与配合用法**：快捷键、自定义配置、跨设备同步、与其他功能的联动。
4. **边界与注意事项**：大小限制、不支持的情况、故障降级行为。

### 3. 部署与外部集成指南（`docs/deployment/*.md`、`docs/cloudflare-tunnel.md`、`docs/tailscale.md`）

1. **适用场景与选型**：先说明这种部署方式适合谁、有哪几种模式可选。
2. **前置条件**：列出必需的系统、权限、账号或端口要求。
3. **分步配置**：按实际执行顺序编号，每步给出可直接复制的命令或界面填写项，并说明预期结果（怎么验证成功）。
4. **运维细节与故障排查**：状态文件路径、配置优先级、常见报错表放在最后。

## 工作流（Workflow）

每次修改代码或专门整理文档时，按以下步骤执行：

1. **盘点变更与受影响页面**
   - 检查本次（或近期）提交改动了哪些用户可见行为：界面入口位置、按钮/选项名称、默认行为、新增字段、命令行参数或配置项。
   - 对照以下清单逐一核对是否需要同步：
     - `README.md` 与 `docs/overview.md`（核心卖点、支持列表、截图说明）
     - `docs/README.md`（新增或拆分的文档入口）
     - `docs/usage.md` 及 `docs/usage/*.md`（日常使用、界面入口与交互）
     - `docs/hybrid-sessions.md`、`docs/cli-agents.md`（Agent 列表、混合模式、权限与连接器）
     - `docs/deployment.md` 及 `docs/deployment/*.md`（安装、配置、服务、托盘）
     - `docs/protocol/`（API 字段、状态码与 WebSocket 帧）
     - `docs/faq.md`（常见疑问与排障入口）
     - `docs/website.md` 及 `docs/website/*.md`（官网引用的仓库事实与证据点）
     - `docs/user-stories/` 及索引（见 [User Stories 维护](../../../docs/agent-rules/user-stories-maintenance.md)）
2. **检查新手指引与阅读动线**
   - 假设自己第一次打开这页文档：前十秒能不能看懂核心概念？
   - 如果一个新功能（如快速开始、初始化指令、工作树收窄）被塞进了某段密集的说明里，把它提炼成清晰的步骤或独立列表项，先讲“怎么用”，再讲“规则与边界”。
3. **检查規模与树状拆分**
   - 单文件严格保持 20–400 行、不超过 48 KiB，单行不超过 300 显示列（围栏代码块豁免，表格行不豁免）。
   - 文件超过 360 行或 44 KiB 时，**先按主题拆分到同名子目录，再新增内容**，绝不靠删减事实或把多句话塞进一行来凑行数。
   - 拆分或移动章节后，用 `git grep` 搜索全仓指向原文件及 `#锚点` 的链接并一并更新（注意目录层级变化后的 `../`）。
4. **格式化与门禁验证**
   - 运行 `make format` 格式化 Markdown。
   - 运行 `make docs-check`（执行 `internal/docguard` 的规模、行宽、可达性、锚点与 README 预算检查）。
   - 如果修改了 `AGENTS.md` 或 `docs/agent-rules/`，运行 `go test ./internal/archtest -run TestAgents`。
5. **在交付说明中交代影响范围**
   - 列出更新或拆分的文档路径、新旧锚点对应关系（如有迁移），以及同步更新的 User Story ID（或说明无故事变更的原因）。

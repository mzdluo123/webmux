## Context

- 现状（已读代码）：
  - `internal/hybrid/eventlog.go` 的 `chatLog` 是内存事件日志，上限取 `scrollback_bytes`（`defaultScrollbackBytes = 2 << 20`），按 `eventSize` 估算计量（每事件 96 字节加每字段 16 字节再加文本长度，忽略转义）；超出时 `append` 从头部丢弃最早的事件，直到只剩一条或不再超出，并置 `truncated`。
  - `translate.go` 不合并流式块：每个 ACP 文本块一个 `message.append` 事件；`messageId` 是 agent 提供的，或服务端按角色连续块分配的 `wmN`。
  - 单个字段上限 `maxFieldBytes = 256 KiB`，因此一次整文件读取或长命令输出就可以占掉预算的相当一部分。
  - `hub.Chat` 把 `Subscription.Events`（全部缓存事件或续接点之后的事件）编码成一个 `events` 帧；实时帧逐个 `Frame` 推送。
  - 订阅时 `subscribe` 在同一把锁下取得快照、事件与注册，保证无缺口；`resume.Seq` 在 `[from, next]` 内才增量补发，否则 `Reset`。其中起点用 `start = int(resume.Seq - from)` 直接当切片下标，隐含“日志里的序号连续”这一假设；合并之后这个假设不再成立。
  - 日志事件的其他消费者：`internal/sessioncmd/streams.go` 的 `turnWait` 按 `messageId` 连接 agent 文本，对合并事件与组内补发都兼容；`wire.ChatEvents` 的 `From` 取首个条目序号，前端的 `events` 帧处理不使用它。
  - 前端 `chat-model.ts` 的 `applyEvent` 以 `event.seq < model.next` 去重，并把 `next` 设为 `event.seq + 1`；续接点是 `model.next - 1`。`seq` 的空洞不会出错。`message.append` 把文本接到同 ID 消息后，`tool.upsert` 的 `content` 整体替换。
  - `ToolRow.svelte` 已在内容块 `truncated` 时显示“（内容过长，已截断）”。
- 度量（`replaysize` 脚本，合成会话）见 proposal；本设计的阈值来自那次度量，实现前要在仓库内用确定性测试复现（见 tasks 第 1 节），不依赖该脚本。

## Goals / Non-Goals

**Goals:**

- 同一份预算保留更多对话轮数，同时不丢失标题、状态、位置与最近的完整 tool 输出。
- 续接语义保持“已有内容不闪烁、不重复、不遗漏”，包括断线时恰好落在被合并的消息中间的情形。
- 不改线上协议与前端模型；改动集中在 `internal/hybrid` 的日志。

**Non-Goals:**

- 不改变 `scrollback_bytes` 的含义、默认值或终端缓冲。
- 不做首屏只发尾部、分页或按需向前加载。
- 不丢弃 tool 调用本身，不改变 `tool.upsert` 的补丁语义，不改变 permission / form 请求与计划等事件。
- 不压缩内存中的事件（如对旧事件做 gzip）。

## Decisions

### 1. 降级只在超预算时发生，并保护最近一段

- `append` 在 `bytes > capacity` 时，先降级，降级后仍超出再按现状丢弃最早事件。
- 保护窗口：从日志尾部起累计估算大小不超过 `capacity / 4` 的事件不降级。常量写成包内可调整的值，便于度量后微调。
- 窗口按累计大小定义：单个事件本身就超过窗口时，它不在窗口之内，同样可以降级。这样在边界情况下优先保留对话，而不是为了保住一个巨大的 tool 输出驱逐更早的对话；实时订阅者已经收到的完整内容不受影响。
- 为什么不一开始就降级：未超预算的会话保持完整输出，行为与现在一致，也避免“刚刚展开看过的输出被缩短”。

### 2. 降级的形式

- 对事件 `Tool.Content` 的每个块：`Text`、`NewText`、`OldText` 各自截到至多 2 KiB（在 UTF-8 字符边界处），并置 `Truncated = true`。`Type`、`Path`、`URI`、`Name`、`MimeType`、`Unsupported`、`Locations`、`Title`、`Status`、`Kind` 不变。
- 事件序号与种类不变；构造新的 `Event`、`Tool` 与 `Content` 切片，不修改已存储的对象（日志的事件对订阅者共享，保持不可变）。
- 已不超过 2 KiB 的块不动，所以降级是幂等的。
- 度量对应（400 轮会话、2 MiB 估算预算）：2 KiB 约保留 76 轮，现状 57–66 轮；限制到 512 字节为 83 轮；完全丢弃为 91 轮。选 2 KiB 是为了让折叠后展开仍能看到命令的头部输出与 diff 的开头，收益比丢弃略低但风险小。
- 续接安全：降级只影响比保护窗口更旧的事件。已经收到这些事件的客户端不会再次收到它们；尚未收到的客户端本来就没有这部分内容，直接拿到降级版本。
- `ToolRow` 显示的文案“（内容过长，已截断）”对降级内容不完全准确。本变更不改文案，避免触发 UI 截图等要求；是否改为“（内容已截断）”留作开放问题。

### 3. 相邻同消息块的合并存储

- 触发时机：日志追加一个事件时，若尾部存在一组“已封存”的块，就把这一组合并成一条存储事件。
  - 组的定义：连续的 `message.append` 事件，`messageId` 与角色相同，角色为 `agent` 或 `thought`，且没有附件。
  - 封存条件：后一个事件不是该消息的延续，即种类不同、消息 ID 变化或角色变化。
  - 仍在流式中的最后一组不合并，因此实时推送与活动消息完全不变。
- 合并后的存储事件：
  - `Seq` 取组内最后一个块的序号，使“已应用到这个序号”对客户端意味着整组都已应用，也与 `chat-model.ts` 的去重和 `next` 推进一致。
  - 额外保存首序号 `first` 与每个原块的累计字节偏移 `ends`（每块 4 字节），用于续接。块的序号在组内连续，因为日志只从头部删除事件。
  - `At` 取首块的时间；`Truncated` 取各块的“或”；文本为各块依次连接。
- `from`（快照中的最早序号）取最早存储事件的 `first`。续接判断仍是 `resume.Seq` 在 `[from, next]` 内才增量补发。
- 续接起点不能再用 `resume.Seq - from` 当下标：合并后序号有空洞。改为在存储事件上按序号查找第一个满足 `Seq ≥ resume.Seq` 的事件（事件按序号递增，用二分查找）；找到的事件若 `first < resume.Seq`，说明落在组内，按下一条处理。
- 续接落在组内：客户端已应用到序号 `S`，`first ≤ S < Seq`（即 `resume.Seq` 在组内）。服务端不重发整条合并事件，而是发送一条同 ID 的 `message.append`，文字取偏移 `ends[S - first]` 之后的剩余部分，`seq` 仍为组的最后序号。结果：客户端的文本等于原先所有块的连接，不重复、不遗漏。
- 估算计量按合并后的内容计算：包装开销只算一次，这才是预算增益的来源。
- 锁与不可变性：合并在 `chatLog.mu` 内进行，成本与被合并的组大小成正比，不做阻塞操作；合并构造新事件，不修改共享对象；已经发给订阅者的实时帧不受影响。

### 4. 驱逐顺序与 `truncated`

- 顺序：降级 → 丢弃最早事件。丢弃时按存储事件（可能是合并事件）为单位。
- `truncated` 仍表示“更早的事件被丢弃”，顶部提示“更早的历史未缓存，可切到终端查看”不变。降级本身不置 `truncated`，因为事件仍在，只是内容变短，由 `ToolRow` 的内容块提示。

### 5. 契约与前端不变

- 线上帧结构不变，合并事件与普通事件的形状一致，`tool.content[].truncated` 已存在，所以不需要改 `internal/contract`、`internal/wire`、`web/src/schemas.ts` 与 `wire` 快照。
- 如果实现时发现前端需要新字段（例如展示“已合并”），说明设计有偏差，应先回到本文件修改而不是顺手加字段。

## Alternatives considered

- **只在重放时合并**：不改日志存储，`hub` 在写 `events` 帧时合并相邻块。流量能省约三分之一，但预算利用率不变，而预算才是本变更要改善的；且要在 hub 层处理续接偏移，复杂度并不低。
- **直接丢弃旧 tool 输出**：轮数最多（91 轮），但最近几轮以外的输出展开后全空，与“展开查看”的预期冲突；2 KiB 折中。
- **拆成两个预算**（对话一个、tool 输出一个）：实现简单，但固定比例对输出很少或很多的会话都不合适；降级是按需的。
- **提高默认预算**：增加内存与重放流量，对窄带用户不友好。
- **对旧事件做内存压缩**：保留全部信息，但引入 CPU 开销、解压路径与锁持有时间，复杂度高于收益。
- **重放帧分页（首屏只发尾部）**：收益更大，尤其对 2 Mbps 这类链路，但要新增协议字段与前端加载逻辑，应单独提出。

## Risks / Trade-offs

- 续接是协议正确性的核心：组内续接的剩余文字边界、`first`/`from` 的取值、`Reset` 条件、与降级交互都要有边界测试（包括恰在组首、组尾、组外一格）。
- 合并改变了新订阅者看到的 `seq` 序列（出现空洞）。前端 `chat-model.ts` 与 `sessioncmd` 都不依赖连续性，但 `subscribe` 当前的下标计算依赖，必须随之修改（见决策 3）；实现时再 `grep` 一遍日志事件的消费者，确认没有其他位置假定序号连续（包括测试辅助函数与 `webmux` 命令行客户端）。
- 降级后旧 tool 输出变短，用户刷新后展开旧工具调用看到的内容少于刷新前。这是预期取舍，在用户故事中写明。
- 估算与真实 JSON 的偏差不变（估算偏高，约为实际 JSON 的 1.15 倍）；本变更不调整它。
- 度量来自合成会话：工具调用比例、输出大小与块大小是假设。阈值（2 KiB、四分之一窗口）是可调常量，应在第 1 节复现度量后再确定。

## Migration Plan

- 日志只存在于内存中，没有持久化，不需要迁移。服务重启后清空，行为与现在一致。
- 回滚：还原 `eventlog.go` 的改动即可，线上协议无变化。
- 兼容：新旧前端都按 `seq` 去重，旧版本前端对合并事件与降级事件无感。

## Open Questions

- `ToolRow` 的“内容过长，已截断”文案是否改为通用的“内容已截断”？这是可见 UI 文案变更，需要走 `webmux-ui` 技能与截图要求。
- 保护窗口与降级阈值最终取值，待第 1 节的确定性度量复现后确认；是否值得暴露为配置项，默认不暴露。
- `thought` 角色的块是否合并：本设计包含，因为思考默认折叠且量大；如发现展开状态依赖块边界则排除。

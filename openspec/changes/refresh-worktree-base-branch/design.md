## Context

- 当前 `Service.Branches` 只枚举 `refs/heads/` 与已有 `refs/remotes/`；`defaultBase` 固定为主工作区 HEAD，分支查询没有 upstream 解析或网络操作。
- `WorktreeCreateFields.svelte` 仅在仓库变化时读取分支清单，直接采用 `defaultBase`；现有 `loading` 会阻止创建，不能复用为非阻断 fetch 状态。
- 创建接口已把 `base` 解析为精确 OID，再执行 `worktree add -b ... <oid>`，因此远程刷新只需改变前端选择的基线，不必改变创建接口或让 Git 在创建时隐式选择远程。
- `Service.git` 已设置 `GIT_TERMINAL_PROMPT=0`、`GCM_INTERACTIVE=never` 和有界输出。仓库操作 gate 会串行化现有 Git 操作，但网络 fetch 若持锁，会让用户提交创建等待慢网络。
- 现有 `worktree-lifecycle` 的“不自动 fetch”条款由本变更 delta 明确修订；已有本地分支模式保持无 fetch。

## Goals / Non-Goals

**Goals:**

- 复用现有精确 OID 创建路径，把上游刷新限制为基线发现能力。
- 明确本地回退、远程基线来源和请求时序，使慢网络与过期响应不影响用户操作。
- 保持普通分支清单无网络，并避免并发 fetch 与创建在应用锁层面互相等待。

**Non-Goals:**

- 不增加远程凭据配置、自动重试、定时 fetch、singleflight 或远程仓库缓存。
- 不改变已有分支检出、worktree 创建请求和删除语义。
- 不保证确认创建瞬间远端没有再次前进；保证的是使用界面展示的精确 OID。

## Decisions

### 1. 新增显式刷新接口，普通清单保持离线

新增 `POST /api/repositories/{id}/branches/refresh`，请求体为 `{ "branch": "<本地分支名>" }`。该路由沿用现有认证、Origin、JSON 限制和错误映射；`GET /branches` 不触发网络。

响应始终描述当前可用的默认基线：

- `branch`：本次结果绑定的本地分支名。
- `base`、`baseSubject`：上游 fetch 成功时为上游跟踪引用的精确 OID 与标题，否则为所选本地分支的 OID 与标题。
- `baseSource`：`remote` 或 `local`。
- `upstream`：已配置上游的短名；无上游时为空。
- `fetchWarning`：成功时为空；无上游、失败或超时时为可直接展示的安全说明。

无上游和 fetch 失败属于可降级结果，返回 200 与本地基线；分支不存在、请求非法或仓库不可用仍走既有 4xx/5xx 错误。响应不返回 remote URL、命令行或原始 stderr，避免泄露内嵌凭据。

`contract.Branches` 另增 `defaultBranch`，由主工作区当前本地分支填充，供初始选择使用；不能再通过 `defaultBase` 的 OID 反推分支，因为多个分支可能指向同一提交。同步 `internal/contract`、`internal/wire`、Zod schema 和 wire 快照。

### 2. 只接受已配置上游，不猜测同名 remote

服务先确认请求分支是当前 `refs/heads/` 中的精确本地分支，再通过 `branch.<name>.remote`、`branch.<name>.merge` 与 upstream 跟踪引用解析配置。只有三者形成有效上游时才 fetch；不再回退到 `origin/<branch>` 或“唯一同名远程分支”。

remote 为 `.` 时属于本地上游，不执行网络 fetch，按无远程上游保留所选本地分支并说明原因。该取舍避免把另一个本地分支误标为“远程最新”。

fetch 使用 argv 调用 `git fetch --no-tags <remote> <merge-ref>`，分支名不经过 shell。沿用禁止交互的 Git 环境，使用独立 30 秒超时。成功后重新解析 upstream 跟踪引用及提交标题，并用 `git merge-base --is-ancestor <local> <upstream>` 比较版本关系：

- 本地是上游祖先（含相同提交）：采用远程基线。
- 本地领先或分叉：保留本地并显示“本地分支包含上游未有的提交”。

创建仍只接收解析后的 OID。

### 3. 网络阶段不持有仓库操作锁

上游解析可在现有短读取 gate 内完成，但释放 gate 后才执行网络 fetch；fetch 后再短暂读取跟踪引用。这样创建、清单刷新和其他仓库操作不会等待 30 秒网络超时，Git 自身 ref 锁仍处理实际对象与引用写入竞争。

不引入新的跨请求任务或后台队列：每次 HTTP 请求在自己的 context 中完成，前端取消会终止等待。并行手动刷新由前端代次控制，不在服务层增加去重抽象。

### 4. 起始分支与基线是两个状态

“创建新分支”模式新增本地起始分支选择器。初始值取 `defaultBranch`；主工作区 detached 或该值不可用时保留现有 `defaultBase`，不伪造分支选择。用户改变起始分支时：

1. 立即把基线设为该分支的本地 OID，并清除上一分支的警告和远程标记。
2. 启动对应上游刷新。
3. 成功且结果仍适用时，以响应中的远程 OID 替换基线并显示“远程最新 · <upstream>”。

基线输入仍允许选择或输入其他 commit；新分支名称与目标路径不因刷新响应而改写。已有分支模式隐藏这些控件且不启动刷新。

### 5. 刷新状态独立于创建可用性

新增 `refreshing`、`refreshWarning`、上游标签与本地最后成功刷新时间；初始分支清单的 `loading`/`error` 逻辑不变。`ready` 不依赖 `refreshing`，因此 spinner 与手动刷新按钮的忙碌状态不会禁用基线、路径、新分支名称或创建按钮。

手动刷新按钮使用现有设计系统按钮/尺寸和本地 Tabler 图标；图标按钮提供可访问名称、可见 tooltip，等待时使用旋转进度图标。最近刷新时间只保存在面板状态中，不进入持久化或服务端契约。

### 6. 用请求代次和用户编辑版本防止回写竞争

组件维护递增的刷新代次，以及仅在用户手动编辑基线时递增的编辑版本。每次自动或手动刷新捕获 `repository.id`、起始分支、代次和编辑版本；分支变化、仓库变化、切到已有分支模式或卸载时递增代次并中止前一请求。

响应只有同时满足以下条件才更新基线：代次最新、仍为新分支模式、仓库和起始分支一致、编辑版本未变化。用户在手动刷新之前已经输入的基线可被该次显式刷新更新；请求发出后的新输入必须保留。警告与远程标签也按同一代次应用，避免旧失败污染新分支状态。

### 7. 失败降级与诊断边界

无上游、fetch 失败和超时都保留已经可见的本地 OID；`baseSource=local` 防止界面把回退值标成远程最新。警告提供“无上游”或“刷新失败，可重试”的用户级原因，详细 Git 诊断仍由用户在终端处理。HTTP 请求本身失败时保留当前 OID，但清空既有远程来源标签与刷新时间，避免与失败警告同时显示“远程最新”。

若 fetch 实际更新了跟踪引用但随后读取失败，不利用该次未知结果；仍返回本地基线和警告。若用户已在刷新期间提交创建，创建使用当时可见 OID，后续响应不能 retroactively 改变已提交请求。

## Risks / Trade-offs

- [fetch 与 worktree 创建并发可能短暂争用 Git 锁] → 不在应用层串行等待网络；让 Git 返回可解释冲突/失败并沿用现有刷新与错误语义。
- [仅支持已配置上游会让部分同名远程分支无法自动刷新] → 明确显示无上游和本地回退，不猜测 remote；用户可在终端配置上游后手动刷新。
- [降级响应隐藏具体认证或远端错误] → 避免 remote URL/凭据泄露，保留可重试说明；详细诊断不进入浏览器契约。
- [远端可能在 fetch 后再次前进] → 界面表述为“本次刷新的上游最新”，创建固定使用显示 OID，不承诺持续同步。
- [多个面板可同时 fetch 同一分支] → 首版接受额外网络请求；只有实际出现负载问题再评估去重，避免提前引入共享任务生命周期。

## Migration Plan

- 无持久化迁移或配置新增；`defaultBranch` 和刷新接口均为增量契约，前后端随同一二进制发布。
- 旧前端继续读取现有 `defaultBase`，不会调用刷新接口；新前端依赖同版本后端提供的 `defaultBranch`。
- 回滚时移除刷新路由与 UI 即恢复原本地基线行为，已创建 worktree 不受影响。

# Design

## Context

配对请求目前只有公钥与 rebind；host ID 由 Relay 创建，本地遗失绑定时无法用它证明同机。
Relay 已有完整 GitHub 授权、单账号单宿主、代际 CAS 和撤权流程，本变更复用这些边界。

## Goals / Non-Goals

**Goals:** 机器身份独立于绑定；同机恢复不额外确认；不同机器和旧记录保持显式确认。
**Non-Goals:** 不采集硬件指纹，不让机器 ID 代替登录，不增加每账号多宿主，不自动开启公网入口。

## Decisions

- 新增公开 `MachineID`，使用 32 个随机字节的无 padding base64url 编码；空值仅用于兼容旧客户端和旧记录。
- 仅扩展配对请求的可选 machineId，不在 Binding、状态、URL 或日志增加机器 ID；两仓固定同一协议提交。
- `relay-machine.json` 使用已登记 statefile typed handle 和独立生命周期锁；只在首次配对前创建，解绑与 Relay 设置删除不删除它。
- 损坏、锁冲突和落盘失败阻止配对，保留原文件；机器 ID 不从公钥、账号或 /etc/machine-id 派生。
- 客户端通过控制器将稳定机器 ID 传给配对客户端；未配对界面也显示显式替换入口，沿用已有危险操作确认。
- Relay 在授权后的账号作用域比较机器 ID，自动恢复与显式重绑走同一个事务、代际递增和撤权路径。
- 旧数据库记录保留空机器 ID，首次显式重绑才关联新 ID；不通过同账号直接猜测同机。
- 账号控制台的删除使用已登录所有者会话、同源/CSRF 和绑定代际校验，复用绑定撤销而不直接删除数据库行。
- 删除后保留安全墓碑和固定域名，从列表移除；已撤销记录允许后续普通配对重新授权恢复，活动记录仍严格执行同机或显式替换检查。
- 删除响应只有在旧访问已撤销时标记 complete，未完成时界面保持待确认并以同一宿主及代际重查，不能误删新的绑定。

## Risks / Trade-offs

- [整个状态目录丢失或复制] → 丢失时要求明确替换，复制者仍必须通过账号授权；机器 ID 不是硬件证明。
- [旧客户端回滚不理解新字段] → 服务端先升级，新增列可空；回滚客户端不改变服务端自动恢复策略，旧客户端仍需显式重绑。
- [旧绑定被替换后继续访问] → 复用已认证撤权与 ACK/离线边界，不提前宣布完成。

## Migration Plan

先验证并发布共享协议，再验证双端与数据库迁移；备份生产数据库、配置和二进制。
先部署 Relay 控制面及数据节点，再原子替换本地二进制；不从当前任务内部强制重启承载任务的 WebMux。
部署阶段不删除、恢复或替换当前生产绑定。没有机器 ID 的旧记录由用户日后明确恢复；GitHub 授权必须由用户完成。
回滚保留新可空列和机器身份文件，不恢复旧授权或降低绑定代际。

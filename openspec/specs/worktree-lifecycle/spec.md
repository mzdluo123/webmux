# worktree-lifecycle Specification

## Purpose

允许用户在已注册的本机 Git 仓库中发现、创建和清理工作树，为多个命令行 agent 提供明确的目录隔离。删除行为区分默认保护与用户明确授权的破坏性操作，避免将关闭会话、移除注册、删除目录和删除分支混为一谈。

## Requirements

### Requirement: 展示实际 Git 工作树状态

系统 SHALL 发现已注册仓库的主工作区和所有已有 linked worktree，不论其由 WebMux 还是外部工具创建。每项 SHALL 展示规范化路径、主工作区标记、分支或 detached HEAD、可用性、锁定原因及修改状态；状态不可读取时 SHALL 显示未知/错误而非干净。忽略文件 SHALL 与普通未跟踪文件区分，并在删除风险中体现。

#### Scenario: 外部创建和修改 worktree

- **WHEN** 用户在终端创建 worktree、切换其分支或修改文件后刷新仓库
- **THEN** 页面展示实际 worktree 清单、当前分支和修改状态，不依赖 WebMux 自己创建的记录

#### Scenario: 目录缺失或工作树锁定

- **WHEN** Git 清单中的 worktree 路径缺失、可 prune 或处于 locked 状态
- **THEN** 页面展示对应原因；缺失目录不可启动会话，锁定不被描述为 agent 独占锁，也不触发自动清理

#### Scenario: detached、bare 与未产生提交的仓库

- **WHEN** 仓库包含 detached HEAD worktree、bare 根条目或尚无提交的主工作区
- **THEN** detached worktree 展示提交标识且可启动；bare 根条目不作为会话目录；没有可解析基线时禁止创建 linked worktree并解释原因，但可用的普通工作区仍能直接启动

### Requirement: 明确创建目标路径与分支

系统 SHALL 支持两种互斥创建模式：从明确基线创建新分支，或使用未在其他 worktree 检出的已有本地分支。默认目标路径 SHALL 位于仓库旁的 `<仓库名>.worktrees/<目录名>`，并在提交前可见、可修改。系统 SHALL NOT 覆盖已有目录、重置已有分支、绕过分支占用保护或自动复制未提交修改和环境文件。

#### Scenario: 创建新分支 worktree

- **WHEN** 用户选择可解析的基线、输入合法且不存在的新分支及未占用目标路径并确认
- **THEN** 系统创建对应 linked worktree，返回实际路径和分支，并在仓库分组中展示，即使尚未启动会话

#### Scenario: 使用已有本地分支

- **WHEN** 用户选择未在任何 worktree 检出的本地分支创建工作树
- **THEN** 系统检出该分支且保留其原有提交，不新建同名分支或隐式选择远程分支

#### Scenario: 名称、路径或分支冲突

- **WHEN** 分支名非法、目标路径已存在、目标与已知工作树发生嵌套冲突，或提交时分支已被其他工作树占用
- **THEN** 创建失败并返回具体原因，不覆盖文件、不强制检出，也不退回原目录启动 agent

#### Scenario: 创建失败后的可见状态

- **WHEN** Git 创建过程中失败或请求被取消，但实际已留下分支或 worktree
- **THEN** 刷新以实际 Git 状态为准展示结果，错误说明可能的残留；系统不以递归删除或强制删除分支进行隐式回滚

### Requirement: 安全删除保护目录和运行会话

默认删除 SHALL 要求目标是未锁定的 linked worktree，没有尚未退出的 WebMux 会话，且满足以下两种可验证状态之一：

1. 目录存在、身份与 Git 状态可验证，且没有未提交修改或未跟踪文件（存在忽略文件时在预览中给出丢失警告，不阻止安全删除）；
2. 目录经确认已不存在（`os.ErrNotExist`）且在 Git 清单中处于 `prunable` 待清理状态。

保护范围 SHALL 包含启动目录位于目标及其子目录的直接会话，不仅限于带关联标签的会话。删除行为遵循以下边界：

- 删除 SHALL 仅通过 Git 移除工作树及管理登记，不执行任意递归目录删除，也不清理未选中的其他 `prunable` 登记；
- 删除 SHALL 保留本地分支与已退出普通会话记录；
- 删除 SHALL 保留已归档混合会话记录，并在 `HEAD` 提交可解析时标为已释放空间（目录已缺失的 `prunable` 目标回退使用 Git 登记记录的 `HEAD` 校验提交）。

#### Scenario: 删除干净且空闲的工作树

- **WHEN** 用户确认安全删除符合条件的 linked worktree
- **THEN** 工作树目录及 Git 登记被删除，其分支仍存在，已退出会话仍可查看缓冲并手动移除

#### Scenario: 存在忽略文件但无修改与未跟踪文件

- **WHEN** 用户对仅包含 Git 忽略文件（如 `node_modules`）且无活动会话的 linked worktree 预览并确认安全删除
- **THEN** 预览展示忽略文件将随目录一并丢失的警告但不阻止安全删除；确认后工作树被删除且保留分支

#### Scenario: 清理目录已缺失的未锁定 prunable 登记

- **WHEN** 某 linked worktree 目录已被外部删除、Git 标记为 `prunable` 且未锁定、无运行中会话，用户在页面预览并确认安全删除
- **THEN** 系统移除该条失效的 Git 工作树登记而不影响仓库内其他 `prunable` 项；其分支保留，原路径下的已归档混合会话记录按登记中的 `HEAD` 提交标为已释放空间

#### Scenario: 有修改、未跟踪文件或运行会话

- **WHEN** 用户对包含未提交修改、未跟踪文件或运行中会话的工作树执行默认删除
- **THEN** 系统拒绝并说明阻塞原因，不关闭会话或删除文件，用户可取消、手动处理或进入独立的强制删除流程

### Requirement: 强制删除必须明确授权破坏范围

系统 SHALL 提供独立二次确认的强制删除流程。

- 确认界面 SHALL 展示规范化目标路径、分支/提交、将停止的会话以及丢弃所有目录内容的警告。
- 用户 SHALL 输入目标完整路径，并明确同意停止列出的会话。
- 确认后的执行 SHALL 先阻止 WebMux 向目标创建新会话，等待关联进程清理及 PTY 排空完成，再删除 worktree。
- 会话关闭或终端记录移除 SHALL NOT 自行触发 worktree 删除。

#### Scenario: 强制删除运行中的脏工作树

- **WHEN** 用户完成针对当前目标和会话集合的二次确认
- **THEN** 系统结束列出的 WebMux 会话并等待退出完成，然后强制删除工作树；分支保留，会话退出记录及已有缓冲保留

#### Scenario: 取消确认或确认后新增会话

- **WHEN** 用户取消确认，或执行时发现目标身份/关联会话集合已改变
- **THEN** 系统不关闭任何会话也不删除工作树；状态改变时要求重新预览并确认

#### Scenario: 清理失败或超时

- **WHEN** 关闭会话无法在操作期限内完成，或随后 Git 删除失败
- **THEN** 系统报告失败，不使用递归删除兜底；已关闭会话不自动重启，实际残留工作树在刷新后继续展示

#### Scenario: 主工作区、锁定或不支持安全清理的目录

- **WHEN** 用户尝试强制删除主工作区、locked worktree、含子模块/嵌套仓库的目录，或无法验证身份/状态的目标
- **THEN** 系统拒绝，解释需要在终端处理的原因，不自动解锁，不使用双重 force，也不删除其内部仓库

### Requirement: 创建和删除竞争具有可解释结果

系统 SHALL 协调 WebMux 发起的同一工作树创建、启动和删除操作。删除获得执行权后，新启动 SHALL 被拒绝；启动先成功则安全删除 SHALL 被会话阻塞，强制删除 SHALL 将该会话纳入重新确认范围。外部 Git 操作不受 WebMux 控制，冲突 SHALL 返回错误并刷新实际状态，而不是宣称文件系统已被全局锁定。

#### Scenario: 两个客户端同时启动和删除

- **WHEN** 一个客户端删除工作树，另一个客户端从该目录或其子目录启动会话
- **THEN** 服务只允许符合上述顺序的结果，不成功返回一个启动在已由本次操作删除目录中的会话

#### Scenario: 外部进程在确认期间写入

- **WHEN** 终端之外的进程在删除确认期间继续修改文件
- **THEN** 默认删除重新检查并拒绝不安全状态；强制删除遵循用户已确认的“删除时全部内容”范围，页面明确其无法保护外部进程和确认后写入的数据

### Requirement: 起始分支驱动上游基线

创建新分支时，系统 SHALL 允许用户在可搜索列表中选择本地分支或远程跟踪分支作为起始分支，并在初始选择或选择变化后异步 fetch 对应上游或远程：

- 本地分支尖端或已缓存远程分支尖端 SHALL 立即可用作基线；
- 对本地分支，fetch 成功后本地为上游祖先时 SHALL 采用上游跟踪引用并标明远程来源，否则 SHALL 保留本地尖端并说明；系统 SHALL NOT 为无上游的本地分支猜测 remote；
- 对远程跟踪分支，fetch 成功后 SHALL 采用其最新远程提交。

#### Scenario: 上游领先本地分支

- **WHEN** 用户选择的本地分支配置了上游，且 fetch 后上游跟踪引用指向更新提交
- **THEN** 界面将默认起始提交更新为该上游提交的精确 OID，显示提交标题和远程来源，创建时从该提交建立新分支

#### Scenario: 本地分支领先或分叉于上游

- **WHEN** 用户选择的本地分支包含上游未有的提交，无论上游是否也有本地未有的提交
- **THEN** fetch 后界面保留本地分支尖端并说明原因，不把默认基线回退到较旧或已分叉的上游提交

#### Scenario: 切换起始分支

- **WHEN** 用户把起始分支从一个本地分支切换到另一个本地分支
- **THEN** 界面立即展示新分支的本地提交并异步刷新新分支的上游，不复用上一分支的基线

#### Scenario: 起始分支没有上游

- **WHEN** 用户选择的本地分支未配置上游
- **THEN** 系统不执行 fetch，保留该分支本地尖端作为基线并说明没有上游，不选择同名远程分支或其他 remote

#### Scenario: 使用已有本地分支模式

- **WHEN** 用户切换到“使用已有分支”模式
- **THEN** 系统不自动 fetch，且继续直接检出所选本地分支而不改用其上游提交

### Requirement: 上游刷新不阻塞创建

上游刷新 SHALL 显示进行中和最近刷新状态，并提供手动刷新入口。刷新期间用户 SHALL 能修改所有创建字段并使用当前可见基线提交。无上游、fetch 失败或超时 SHALL 保留本地基线并显示非阻断说明；普通分支清单查询 SHALL 保持无网络行为。

#### Scenario: 刷新尚未完成时创建

- **WHEN** 上游 fetch 仍在进行，用户已填写合法的新分支和目标路径并确认创建
- **THEN** 系统使用界面当前可见的精确基线提交创建 worktree，不等待 fetch，也不禁用创建操作

#### Scenario: fetch 失败或超时

- **WHEN** 上游 fetch 因离线、认证失败、远端拒绝或超时未完成
- **THEN** 界面保留本地分支尖端，显示可重试的非阻断警告，不把该基线标记为远程最新，也不阻止创建

#### Scenario: 用户手动刷新

- **WHEN** 用户点击“刷新上游”
- **THEN** 系统重新 fetch 当前起始分支的已配置上游，成功后更新远程基线和刷新状态；按钮请求期间显示进度但不阻塞其他字段

### Requirement: 刷新结果不得覆盖较新的用户意图

每次上游刷新 SHALL 绑定发起时的仓库和起始分支。只有结果仍对应该选择，且用户未在请求发起后手动修改起始提交时，系统 SHALL 自动替换基线。面板关闭或模式切换后的结果 SHALL NOT 修改新上下文。

#### Scenario: 较早请求晚于分支切换完成

- **WHEN** 分支 A 的 fetch 尚未完成时用户选择分支 B，随后 A 的响应到达
- **THEN** 系统丢弃 A 的响应，B 的本地或上游基线不被 A 覆盖

#### Scenario: 用户在刷新期间修改基线

- **WHEN** 用户发起自动或手动刷新后手动输入其他起始提交，随后刷新响应到达
- **THEN** 系统保留用户输入，可展示刷新完成状态，但不把输入替换为上游提交

#### Scenario: 刷新期间关闭面板或切换模式

- **WHEN** 用户在上游刷新完成前关闭创建面板或切换到已有分支模式
- **THEN** 系统取消或忽略该请求，不重新打开面板、不切换基线，也不影响后续创建上下文

# git-index-staging-and-commit Specification

## Purpose

定义针对真实 Git 索引（index）的文件级与普通文本代码块级暂存/取消暂存契约，以及完整索引提交预览、钩子执行、锁冲突边界与外部并发条件下的提交归属识别和结果核对规则，确保用户所见预览与实际产生的 Git 提交严格可验证且绝不静默失配。

## Requirements

### Requirement: 绑定内容身份的文件级与文本代码块级暂存及取消暂存

系统 SHALL 在经过核实的工作树上下文内操作真实 Git `index`，支持文件级与普通文本代码块（hunk）级的暂存（`Stage`）和取消暂存（`Unstage`），使终端与 CLI agent 能够即时观察到一致的暂存状态，且同一文件在部分暂存后可同时出现在未暂存（`index -> worktree`）与已暂存（`HEAD -> index`）两组中。

每次暂存或取消暂存操作 MUST 遵守以下内容身份与边界规则：

- 请求 MUST 绑定服务端捕获的内容快照及比较两端的精确身份（文件级绑定路径、模式、索引对象 OID 与工作区文件内容摘要；代码块级额外绑定目标差异块在快照中的确定性标识或边界摘要），SHALL NOT 接受客户端在未校验原内容一致性的情况下直接提交任意行号或自由补丁。
- 执行写入前，系统 MUST 在工作树协调保护下复核目标路径在索引与工作区（或 `HEAD` 与索引）中的当前内容及文件模式仍与快照一致；一旦外部 agent 或终端已改写该文件或索引，系统 MUST 拒绝套用旧动作并返回版本过期冲突，保留原工作区内容不变。
- 普通文本代码块暂存/取消暂存 SHALL 正确保留文件原有行尾（`LF` / `CRLF`）、文件末尾无换行符语义（`No newline at end of file`）及可执行文件位（`100644` / `100755`），并支持尚未诞生 `HEAD` 的空仓库首次暂存与取消暂存。
- 取消暂存 MUST 仅更新 Git `index`（恢复为 `HEAD` 对应条目或在未诞生 `HEAD` 时从索引移除），SHALL NOT 删除或覆盖工作区文件内容。
- 特殊条目与冲突路径 MUST 按类型执行明确降级或拦截：
  - 二进制文件、符号链接、子模块（`160000`）、纯重命名/模式变更、超过文本上限的文件，以及配置了 `filter` 或 `working-tree-encoding` 属性导致无法可靠往返映射原始行的路径，SHALL 明确降级为仅允许整文件级操作并说明不支持逐块操作的原因；
  - 处于未解决合并冲突（索引 stage `1..3`）的路径 SHALL 拒绝普通暂存并引导进入冲突处理。

#### Scenario: 同文件双代码块只暂存其一且终端可见

- **WHEN** 同一文本文件包含上下两个互不重叠的未暂存修改块，用户仅对第一个代码块执行暂存
- **THEN** 真实 Git `index` 仅吸收第一个代码块，该文件同时出现在已暂存（含第一块）与未暂存（仅剩第二块）列表中，工作区文件完整保留两处修改，包括末尾无换行或 `CRLF` 格式

#### Scenario: 阅读后文件已被外部 agent 修改

- **WHEN** 用户打开某文件的差异快照后，后台 agent 修改了该工作区文件，用户随后基于旧快照点击暂存其中一个代码块
- **THEN** 系统检测到当前工作区内容摘要与快照不一致，以快照已过期拒绝写入，`index` 与工作区新内容均不被覆盖

#### Scenario: 过滤属性与二进制文件降级

- **WHEN** 仓库中存在配置了 LFS/`filter` 属性的文本文件与一张修改后的 PNG 图片
- **THEN** 系统为这两项标记不支持代码块级暂存的原因，仅允许经内容身份校验的整文件暂存与取消暂存

### Requirement: 完整真实索引提交预览与前置阻塞检查

系统 SHALL 在执行任何提交前生成绑定工作树身份的完整提交预览，提交范围 MUST 严格等于该工作树当前的完整真实 Git `index`，SHALL NOT 仅展示本次页面刚点击暂存的子集，也 MUST NOT 在提交时隐式执行全工作区暂存（如 `git add -A`）。

提交预览 SHALL 包含并校验以下内容：

- 目标仓库、工作树路径、当前分支状态（正常分支、游离 `HEAD` 或未诞生 `HEAD` 首次提交）、预览绑定的当前 `HEAD` OID（若有）以及完整已暂存树摘要与全部已暂存文件列表；若终端此前已暂存文件 `A`、页面本次暂存文件 `B`，预览 MUST 同时列出 `A` 和 `B`，并提示仍留在未暂存/未跟踪中的剩余修改数量。
- 提交作者身份（`user.name` 与 `user.email`）的当前生效配置摘要，以及是否启用提交签名或存在可执行提交钩子。
- 存在以下任一情形时，预览 SHALL 返回明确的阻塞项且不签发可执行确认凭证：
  - 暂存区为空（无任何相对 `HEAD` 的索引差异）；
  - 存在未解决冲突条目（unmerged index entries）；
  - 工作树正在进行未完成的 `merge`、`rebase`、`cherry-pick`、`revert` 或 `bisect`；
  - 缺少 `user.name` 或 `user.email` 配置；
  - 当前处于游离 `HEAD`（引导先创建或切回分支）。
- 系统 MUST NOT 擅自修改用户全局 Git 配置、关闭提交签名或跳过钩子。

#### Scenario: 终端已有暂存项时的完整预览防隐藏提交

- **WHEN** 终端会话已预先 `git add a.go`，用户随后在界面暂存 `b.go` 并请求提交预览
- **THEN** 提交预览完整列出 `a.go` 与 `b.go` 作为本次提交内容，同时标出其他未暂存文件不会进入本次提交

#### Scenario: 空暂存区或缺少身份配置时阻止提交

- **WHEN** 暂存区为空，或运行环境未配置 `user.email`，调用方请求提交预览
- **THEN** 预览返回具体阻塞原因与下一步指引，不生成确认凭证，也不创建空提交

### Requirement: 尊重钩子与锁边界的提交执行及并发结果识别

确认执行提交时，系统 SHALL 校验确认凭证有效且在工作树级协调锁内复查工作树身份、`HEAD` 与完整索引树摘要均未偏离预览；若预览后外部终端或 agent 已修改 `index` 或推进 `HEAD`，系统 MUST 使该次确认失效并拒绝启动 `git commit`，保留用户提交说明草稿供重新预览。

实际执行 `git commit` 及结果核对 MUST 遵守以下边界：

- **正常写入环境**：提交命令 MUST 在尊重仓库 `pre-commit`、`prepare-commit-msg`、`commit-msg`、`post-commit` 钩子、内容转换过滤器与 GPG/SSH 签名配置的非交互环境下执行，SHALL NOT 套用只读运行器的过滤器禁用覆盖，也 SHALL NOT 添加 `--no-verify`。
- **Git 锁冲突不破坏现场**：若外部进程正持有 `.git/index.lock` 或引用锁导致 Git 报告锁占用，系统 MUST 返回“仓库正被其他进程占用”的失败状态，严禁自动删除任何 `.git/*.lock` 文件。
- **精确归属识别与防外部提交误认**：
  - 系统 MUST 为本次提交注入唯一操作归属标识（如绑定本次操作 ID 的强制 reflog 记录），在命令退出后定位确属本次调用创建的提交 OID，SHALL NOT 仅读取最新 `HEAD` 就认定其为本次提交结果；
  - 若命令退出后外部 CLI 立即在同一分支追加了新提交，系统仍 MUST 准确识别本次创建的提交 OID。
- **三态成功/复核/待确认判定**：定位到本次提交 OID 后，系统 MUST 读取其实际 `{oid, parents, tree}` 与预览绑定的预期父提交和预期索引树摘要逐项比对：
  1. 父提交与树摘要完全一致时，状态判定为 `matched`（已按预览提交）；
  2. 提交已创建，但因 `pre-commit` 重新格式化暂存文件、`post-commit` 改写或类似机制导致实际 `tree` 或父提交与预览不一致时，状态 MUST 判定为 `needs_review`（需要复核），返回实际提交 OID 与差异说明，并阻止自动衔接后续推送；
  3. 命令超时、异常中断或极端配置下无法唯一确认是否产生提交时，状态 MUST 判定为 `uncertain`（结果待确认），禁止自动重试或自动重置分支。

#### Scenario: 预览后外部 CLI 修改索引导致确认失效

- **WHEN** 用户已获取提交预览凭证，确认前外部终端在同一工作树执行了 `git add extra.txt` 或 `git commit`，随后用户提交确认请求
- **THEN** 服务端在启动 `git commit` 前检测到索引树摘要或 `HEAD` 已变化，拒绝执行并提示预览已过期，不产生计划外提交

#### Scenario: pre-commit 钩子自动格式化并重暂存文件

- **WHEN** 仓库的 `pre-commit` 钩子在提交过程中格式化了已暂存源码并重新写入索引，使提交成功完成但生成的提交 `tree` 与预览不一致
- **THEN** 系统返回实际生成的提交 OID，但将结果状态标记为 `needs_review` 并提示钩子改变了提交内容，不静默显示“已按预览提交”，也不自动进入推送确认

#### Scenario: 提交刚完成即遭遇外部 CLI 并发追加提交

- **WHEN** 系统执行的 `git commit` 刚创建提交 `C1`，在结果核对完成前外部 CLI 进程已在同一工作树紧接着创建了提交 `C2`（此时 `HEAD` 指向 `C2`）
- **THEN** 系统通过本次操作的唯一归属记录准确返回 `C1` 作为本次提交结果，绝不将外部产生的 `C2` 误报告为本次提交
